# Audit: GPUI track, worlds 06 to 11

Scope: `content/tracks/gpui/worlds/{06-interaction,07-settings,08-widget,09-overlay,10-dashboard,11-screen-time}`.
I read every quest.toml and lesson.md in these six worlds (77 exercises, 1 read quest). I diffed starter against solution for every quest in world 06 and for a sample in 07 to 11 (01, 02, 06, 10, 11 and 16 in 07; 03 and 12 in 08; 02 and 15 in 09; 09 and 12 in 10; 05, 06 and 10 in 11), and opened the tests wherever something looked off.
Reference docs: `docs/CONTENT.md`, `docs/TRACKS.md`, `docs/tracks/gpui.md`, `docs/tracks/gpui-terms.md`, `docs/tracks/rust-terms.md`.
No gpui quest has a `flavours/` folder, so there were no variants to skim.

Two measurements across the whole scope:

- **The lesson's code block is the solution.** In 62 of 77 exercises, the first line of the lesson's ```rust block appears word for word among the lines the solution adds: 06: 10/12, 07: 8/16, 08: 9/12, 09: 13/14, 10: 11/12, 11: 11/11. Most of 07's misses are formatting only (01, 05, 09, 10, 15 are effectively the same). The last hint then repeats it. CONTENT.md says "Never put the solution in the lesson". As built, a beginner copies one line and goes green without having to understand it. An experienced developer gets almost no exercise at all.
- **Quiz answers are almost always the first choice.** 73 of the 75 `[[points]]`/`[[quiz]]` answers in 06-11 are `answer = 0`; the only exceptions are both in 09-overlay. The same holds for worlds 02, 03 and 05, which are 100 % index 0. I found no shuffling in `src/` (I grepped for `shuffle` and `Math.random`). The right answer is also usually the longest, which CONTENT.md forbids. Every point can be won by tapping the top choice.

The "why" content is the strong part of this track. Almost every quest opens with a real product reason: why ids exist, why actions exist, why rename after writing a temp file, why use the median, why 127.0.0.1. Where it falls down is the syntax and the GPUI plumbing: closure shapes, which context `cx` is, derefs, fields that hold functions, conversions. These are used again and again and never laid out.

## World 06: Interaction (6/10)

**Verdict.** The ideas are sequenced well: id, click, hover, tooltip card, graph maths, canvas, actions, menu, tray, boss. The kicker cards give real reasons ("a click is a mouse-down and a mouse-up on the same element, so GPUI has to remember the element between frames"). But this is the world where the listener closure `|this, _, _, cx|` first appears, and its four inputs are never named. Every later world leans on that shape. Ten of twelve exercises are "type the line in the code block". The boss then asks for syntax nothing taught.

**Worst quests**
- `06-interaction/06-draw-the-graph`: the lesson is all about `canvas`, `PathBuilder::stroke`, `move_to`/`line_to` and `paint_path`, but `graph()` is fully written in the starter. The task is one line, `.child(graph(self.points.clone()))`, and it pays 60 XP for 8 minutes. The one new GPUI idea of the quest is never touched, which fails the blind test in reverse: taught, but never practised.
- `06-interaction/01-a-click`: `cx.listener(move |this, _, _, cx| ..)` is shown, but the two `_` (the event and the window) are never explained. "`move` copies `kind` into it" holds only because `StatKind` is `Copy`, which the lesson doesn't say. `SharedString` appears with no gloss.
- `06-interaction/11-tray-icon`: "**Same loop as R5.** Spike R5 checked that tray events arrive while GPUI runs its own message loop." This is internal planning jargon in a learner-facing card.
- `06-interaction/12-boss-interactive-bar`: hint 2 needs struct update syntax (`HoverCard { top: (top_processes)(), ..card.clone() }`) and a call through a field that holds a function (`(top_processes)()`). Neither appears in any lesson. The boss also asks the learner to write `track_focus` with `match &this.ui.focus { Some(focus) => bar.track_focus(focus), None => bar }`, which was starter-only in 08-actions.
- `06-interaction/08-actions`: "`bar_layer` already gives the bar `track_focus` with the handle `focus_in` made" names a `FocusHandle` and a `focus_in` that are never shown. It also never says that `_: &OpenSettings` is how GPUI decides which action a handler is for: the type annotation does the routing. That is the most surprising part of the API for a newcomer.
- `06-interaction/09-right-click-menu`: `.when_some(..)` is used in the code block but never explained; only `.when` was taught (02-views/06). The "Inside the window" card says the bar now runs in a normal window, not docked, so the menu isn't clipped, and that "a pop-up window for the menu is on the plan's list". So the product quietly goes backwards from the world-05 boss, and the plan leaks into the lesson.

**Best quests (models)**
- `06-interaction/03-hover`: the look (`.hover`) is cleanly separated from the state (`.on_hover`), and the "Leave only your own" card explains a real race (RAM: true arriving before CPU: false) in two sentences.
- `06-interaction/05-graph-points`: pure maths with an explicit "Up is smaller" card. It explains y-down, the flat-line divide by zero and `last` ≥ 1, and both objectives test exactly what was taught.
- `06-interaction/08-actions`, intro paragraph: "Settings opens from a left click, the right-click menu, the tray icon, and later a hotkey… four copies to keep in step." This is the model for a "why" opening.

## World 07: Settings (6.5/10)

**Verdict.** This is the most solid "why" world: one global versus copies, clone-then-apply to end a borrow, keep the `Subscription`, window state versus saved state, write a temp file and rename, keep a `.bak`. It is well paced, with pure-maths quests (07 slider maths, 14, 15) between GPUI ones. It slips on components: `Toggle` uses a plain closure where every earlier handler used `cx.listener`, with `&mut App` and `'static` in its type, and none of that is explained. There is also one sequencing slip and a few vague phrasings.

**Worst quests**
- `07-settings/06-a-toggle`: the task is a 12-call style chain (`.p(px(2.))`, `.size(..)`, `.rounded_full()`, two colours, the knob child), and only `.justify_end()` is shown in the lesson. The rest lives in hint 2, so the hint *is* the lesson. The click is `.on_click(move |_, window, cx| on_toggle(!on, window, cx))`, without `cx.listener`. The lesson never says why: a `RenderOnce` component has no `Context<Toggle>`, and the handler gets `&mut App`. `ToggleHandler = Box<dyn Fn(bool, &mut Window, &mut App) + 'static>` sits in the starter with no word on `'static`, or on why the closure is boxed.
- `07-settings/12-drag-to-reorder`: "**Move, not swap.** Alt+Up swapped neighbours." But Alt+Up is the *next* quest (13-keys-to-reorder). This is a forward reference written in the past tense. (01-readings/12 `move_up` swapped slots, but there were no keys then.)
- `07-settings/11-a-long-list`: "`cx.processor(..)` wraps it so it also gets the window view" is unclear. It gets `this`, the `SettingsWindow`. The closure must return a `Vec` of elements, and `.collect()` decides that from the return type, which isn't said either.
- `07-settings/02-settings-struct`: the work is pure data entry. The lesson never states the defaults for `two_lines`, `colours`, `all_taskbars` and `shift_left`, but the test asserts all four. `BTreeMap` is chosen over `HashMap` with no reason given; the reason is a stable key order in the saved JSON.
- `07-settings/01-a-second-window`: the closure `|_, window, _|` in `handle.update` again has unnamed inputs. The "**Not focus-free.**" card is a non sequitur: it describes window options the learner doesn't touch.

**Best quests (models)**
- `07-settings/04-live-preview`: the "Clone, then apply" card explains a borrow-checker trap before the learner hits it, and the Subscription is compared to the dropped `Task` from 03-live.
- `07-settings/14-save-to-disk` and `07-settings/15-fix-bad-values`: concrete failure stories (a crash mid-write, a hand-edited `99`, the Kinetik v3.1.2 bug) with a clear rule each.
- `07-settings/03-a-global`: "keyed by its type", the marker trait, and why a panic is right ("a programming mistake, not a user one"). It works for beginners and for experienced developers.

**Verdict.** Good small, testable steps: snap maths, on-screen check, `relative()`, bit masks, the window stack. The Win32 "why" is clear: let Windows drag, don't overwrite other style bits, Win+D hides desktop widgets. Five of the eleven exercises are a single `match` or a single call (01, 05, 06, 09, 10), so it is light for an experienced developer. Then the boss jumps to a from-scratch `render` that needs a lot of syntax no lesson showed.

**Worst quests**
- `08-widget/12-boss-desktop-widget`: the solution's `render` uses `filter_map(|s| match s { Slot::Stat(k) => Some(*k), _ => None })`, `Option::filter`, `.children(mine.into_iter().map(&row))` (a closure passed by reference), `unwrap_or_else(|| "--".into())`, `collect::<Vec<_>>()`, and a `{ .. }` block whose only job is to end the `self.bar.read(cx)` borrow before `widget_header(cx)`. **Best quests (models)**

### Rewritten example: `06-interaction/01-a-click`, "Then the listener"

Current:

> **Then the listener.** `.on_click(..)` takes a closure. `cx.listener(..)` wraps it so it gets `this`, the bar itself, to change: set `this.ui.clicked` to `Some(kind)` and notify.

Proposed (two cards):

> **Then the listener.** `.on_click(..)` wants something GPUI can run later, when the click happens. `cx.listener(..)` makes it from a closure with four inputs, always in this order: `this`, the `StatsBar` you may change; the event, here a `ClickEvent` this quest ignores with `_`; the `window`; and `cx`, which you need for `cx.notify()`. Every mouse and key handler in this world has this four-part shape; only the event changes.

> **Why a wrapper.** `interactive_pill` runs while the bar is being drawn, and it borrows the bar to do that. The click comes much later, after that borrow has ended. `cx.listener` remembers which bar it belongs to and hands it back to you as `this` when the click arrives, so the closure never has to hold on to the bar itself.

### Rewritten example: `07-settings/06-a-toggle`, new card

> **No listener here.** `Toggle` is a component, not a view: it keeps no state between frames, so there is no `Context<Toggle>` to make a `cx.listener` from and no `this` to hand back. Its `on_click` takes a plain closure that gets the window and `&mut App`, the context of the whole app. That is enough: `on_toggle` changes the `Settings` global, and the bar and the Settings window, which both watch it, redraw.
