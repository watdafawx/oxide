# Curriculum audit: Rust `00-tutorial` and `01-foundations`

Scope: all 3 tutorial quests and all 28 Foundations quests. For each one I read quest.toml and the plain
lesson.md. I diffed starter against solution for every quest except 15, which is a read quest with no code.
I skimmed the games flavours of 00/01, 00/03, 01/05, 01/16 and 01/28. Background I read first:
docs/CONTENT.md, docs/TRACKS.md, docs/REWRITE-rust-00-01.md, docs/PLAYTEST-2026-10-20b-rust-00-03.md
(which audited the *old* 12-quest world) and docs/tracks/rust-terms.md.
I did not run `cargo test`. This is a read-through. The format-string traps in the boss (see W01 worst #1)
come from Rust's format rules, not from a compiler run.

Short version: the 2026-10 rewrite made these worlds much better than the playtest described. The cards are
short and concrete, nearly every quest has a "try the obvious thing → compiler error" moment, and the one-idea
cadence works. What's left is (a) a handful of "furniture" words and syntax that appear from quest 1 and are never
explained (`pub`, `&str`, `usize`, `//`, "parameter", "test", "block"), (b) a few lessons that say something
untrue or contradict an earlier lesson, (c) TODO comments that dictate the code, so for an experienced dev the task
is just typing, and (d) the boss, where six new ideas arrive at once and two TODOs, copied as written, don't build.

## World 00-tutorial (3 quests)

| Beginner clarity | Experienced-dev value | Coherence/sequencing | Task-lesson fit | Overall |
|---|---|---|---|---|
| 6 | 7 | 8 | 8 | **7** |

**Verdict.** It does its one job well: it teaches the edit-save-green loop and how to read `left`/`right`, finishable
in 10 minutes. An experienced dev is through it in three minutes and nothing is padded. For a true beginner it
assumes a lot without a word: what a function is, what "text" or a "value" is, what a test is, why
`pub fn greeting(name: &str) -> String` looks the way it does. The boss uses `let` and `//` comments a world before
they are taught. None of this blocks the task, because the gap is one line, but the first screen is a wall of
unexplained symbols and nothing says "you can ignore these for now".

### Worst quests
- **00/03-boss-name-tag**: the lesson's code block uses `let loud = ...` (`let` is first taught in 01/01) and `//`
  comments (never explained anywhere in 00/01). "Method" is glossed only as "written after a dot". `level: u32` is
  unexplained. "Press Run to see the tags printed" brings in a Run button, and so a program with `main`, that has never
  been mentioned. The idea of a *program that runs*, as opposed to tests, is never taught.
- **00/01-hello**: "Rust drops the value of `name` in there". The lesson never says where `name` comes from (it is a
  parameter) or what a function is. The games flavour reads awkwardly: "A function that gets a player called `player`".
  The tests are mentioned ("tests that tell you when the gap is filled") but never defined.
- **00/02-fix-it**: the lesson's example shows `left: 19` and `right: 20`, which is exactly this quest's answer, so the
  "read the red" exercise is solved before the learner reads anything red. Use different numbers (e.g. 11/12) in the
  lesson. `-> usize` is never explained.

### Best (model)
- **00/02-fix-it**: "Red is information" sets the emotional tone of the whole course. The "Save once, change nothing"
  step makes failure the expected first move. (Change the example numbers.)

## World 01-foundations (28 quests)

| Beginner clarity | Experienced-dev value | Coherence/sequencing | Task-lesson fit | Overall |
|---|---|---|---|---|
| 6 | 5 | 7 | 7 | **6.5** |

**Verdict.** Quests 01-14 and 20-27 are good beginner material. Each is one idea with a real situation, a compiler
moment and a two-function task. The "why" is often given (`mut` exists because changing values are where bugs hide;
enums make the compiler find every place a new variant must be handled). It falls short in three places. Several
recurring words are never taught, only used. A few lessons are wrong or contradict each other (05, 12, 18).
And the boss is a cliff: Vec, `for` over a reference, `return`, `break`, recursion, match-as-binding with early
`return`, multi-statement match arms and statement-`if`, all at once, at 55 minutes. For an experienced dev the world is
slow: 28 quests where every TODO comment spells out the exact code (e.g. 11: "`let mut total = 0;`, a
`for row in 1..=rows` loop that adds `row`, then `total`"). Rust-specific depth they would value is missing or
deferred: overflow wraps in release, `as` is lossy and saturating, `&&`/`||`, `println!`/`main`. The plain flavour's
"packing planner" spine is loose. It wanders into theatre seats, a mail enum, unicorns and a "box book", and its
lessons reuse the games examples (Chest, Mob::Zombie, coal/fuel_burn).

### Worst quests (path: concrete problem)
1. **01/28-boss-crafting-calculator**
   - Six new ideas taught in one lesson: `Vec`/`push`, `for x in &list`, `return`, `break`, recursion, and the
     unstated `let (a, b) = match … { Some(p) => p, None => return Err(..) };` shape. This breaks CONTENT.md's
     "one idea per quest" and its "explain, then ask" rule.
   - **Two TODOs don't build as written.** In `run`, the TODO shows `push "Learned {kit.output}"` and
     `"{count} {item} needs: {totals_line(&calc.raw_totals(&item, count))}"`. Rust's inline format args accept
     only bare identifiers. Field access and function calls inside `{}` are compile errors. The solution correctly
     uses `format!("Learned {}", kit.output)` and a `let list = …` line.
   - Never taught, but the solution needs it: match arms with `{ … }` blocks holding several statements; an `if`/`else if`
     chain used as statements, not as a value (every `if` so far was a value); functions that return nothing
     (`fn take(..) {}`, `expand`); `&item` to pass a `String` where `&str` is expected; comparing `String == &str`.
   - Point 2 asks "Which **word** stops a recursive function…" but the answer is "an arm that does not call itself".
   - Title "Boss: packing planner" sits in folder `crafting-calculator`. That's fine, but it confuses anyone reading the repo.
2. **01/05-how-big-can-a-number-be**: the "Try the obvious thing" card says Rust refuses `after - before -> u32`
   "because the answer might be negative". That is wrong. Rust refuses because the parameters are `i32` and the
   return type is `u32` (a type mismatch). The compiler never reasons about whether a value might be negative.
   With `u32` parameters the same code compiles and panics at runtime, which is exactly 01/07's lesson. This plants
   a wrong mental model of what the type checker does.
3. **01/12-repeat-until**: the "Signed on purpose" card says the pile is `i32` because the last scoop overshoots, and
   "a `u32` cannot do that". Five quests earlier, 01/07 taught `saturating_sub` for exactly this situation. The
   learner has two contradictory rules and no guidance on when to use which. The card also uses the word
   "parameter" as if it were known ("Parameters stay put"). It is never defined; 01/03 says "what goes in". The term
   ledger claims 01/03 introduces it, but it doesn't.
4. **01/20-one-of-a-few**: hint 1 says "Write one `match type { ... }`". The parameter is `kind`, and `type` is a
   reserved keyword, so a learner who copies the hint gets a confusing parse error. The quest also teaches two ideas
   (enum + match) with two code blocks; the rewrite chose this on purpose, but at minimum the hint must be fixed.
5. **01/15-how-rust-thinks (read)**: written for someone who knows other languages: "In many languages… null",
   "There are no exceptions", "throws an exception the caller can catch". A non-programmer has no reference point
   for null or exceptions, so the "why" lands only on people who already knew it. The quiz uses "compile time" and
   "runtime", but the lesson never uses either term. It sits between arrays and structs, eight quests before Option
   and eleven before Result; it would land better just before 23.
6. **01/18-start-from-scratch**: "That type is called an **associated function**". Here "type" means "kind of
   function", in the same world where "type" has just become a technical word (05). Use "That kind of function".
7. **01/13-a-pair**: the TODO says `let (kind, count) = slot;`, which leaves `kind` unused and gives an unused-variable
   warning. The solution quietly writes `_kind`. The underscore-prefix convention is never mentioned.
8. **01/27-handle-both-paths**: `.parse::<u32>()` (the "turbofish" `::<>`) is used with no word on what the `::<u32>`
   part is or why it's needed. The objective label says `describe_quantity(" 12 ")`, but the test calls `"12"` and
   `" 7 "` (a small mismatch).
9. **01/16, 17, 19 (String / `&`)**: `&str` has been in every signature since 00/01. 01/16 finally says a plain
   `"tools"` is "only a borrowed piece of text", 01/17 says `&` is "borrow to look", and 01/19's error says "behind a
   `&` reference". Three different glosses for one symbol, and `&str` itself is never named. One clear card would
   do it: "`&str` = text you are looking at; `String` = text you own; `&` = look, don't take".
10. **Plain-flavour drift (01/10, 11, 21, 23, 24, 25; quest.toml summaries of 17, 19, 21)**: the summaries for 17 and 19
    say "stack" (a games word) in the plain flavour, and 21's says "durability, servings, days". The plain lessons'
    code examples are the games ones (`Chest`, `Mob::Zombie`, `fuel_burn("coal")`, "coal burns 80 ticks"), and 21's
    point asks about `Mob::Zombie` in the plain flavour. The plain units also disagree with each other: in 06 a
    pallet holds 64 sheets, in 10 it holds 64 boxes, and in 03 a sheet makes two boxes.

Smaller:
- 07 shows `thread 'main' panicked`, but under tests the thread is the test's name.
- 07 never says that release builds wrap silently instead of panicking. That is a distinctive Rust fact an experienced
  dev wants, and the lesson's "a debug build" is unexplained jargon for a beginner.
- 09 never explains the precedence of `as` versus `/`, or why `(a + b)` needs brackets; the hint gives
  `(a + b) as f64 / 2.0`.
- 08 never says that `f64` is a "floating-point" number, though `{float}` and "floating-point literal" appear in its
  error text. It never warns that floats are approximate.
- 14: `shelf[5]` with a literal index on a fixed array is a *compile* error, not the runtime panic shown. Show it with
  a variable index.
- 19: plain assignment to a field (`self.boxes = …`) is the first non-`+=` reassignment; it gets one clause in 10
  ("A single `=` gives a name a value").
- 04: `.len()` "counts the letters". It counts bytes; that's fine for ASCII, but say so once for the experienced reader.
- 04: "Most languages would complain" is untrue for Python/JS `var` and meaningless to a non-programmer.

### Best quests (models)
- **01/02-the-count-changes**: the model of the house style. Real situation, the obvious move, the real error code
  (E0384), the word in bold with a gloss, *why* Rust does it, and a habit to take away ("the red message is the plan").
- **01/03-a-rule-you-can-reuse**: reads a function signature piece by piece, and explains the
  expression-vs-statement "trips people" rule in two sentences.
- **01/20-one-of-a-few**: gives the deep why of enums ("add a choice later and the compiler shows you every place").
  This is real value for experienced devs too. Fix the hint.
- **01/24-a-fallback**: "The fallback is a decision… Rust makes you choose rather than guess", plus a clear warning
  about `unwrap`.
- **01/06-full-stacks-and-leftovers**: a tiny quest, a perfect "easy win", and concrete numbers throughout.

1. **Fix the factual and buildability bugs (an hour of work).**
   - 01/28: rewrite the two `run` TODO strings so they show `format!("Learned {}", kit.output)` and a `let list = …`
     line, and add a card: "Inside `{}` you can put a name only. For a field or a call, use `{}` and put it after the string."
   - 01/20: change hint 1 to `match kind`.
   - 01/05: rewrite the "Try the obvious thing" reason (example below).
   - 01/12: either use `saturating_sub` with `u32`, or add one sentence: "07's `saturating_sub` would also work here; this
     quest uses `i32` to show the overshoot."
   - 01/18: change "That type" to "That kind of function".
   - 00/02: use different `left`/`right` numbers in the lesson example.
   - 01/27: make the objective label match the test inputs.
   - 01/28: fix point 2's wording.
2. **Add one "furniture" card early (00/01 or 01/01)** that names everything a beginner sees but does not need yet:
   "`pub` = other files may use this. `//` = a note for humans; Rust ignores it. `&str` = some text. `usize` = a count.
   Everything under `mod tests` is the checker; you never edit it." This one card removes most of the
   unexplained-symbols anxiety at almost no cost to experienced devs.
3. **Split the boss's teaching into three small quests before it** (01/28a `Vec` + `push` + `for x in &list`;
   01/28b `return`/`break` and statement-`if`; 01/28c recursion), then let the boss *use* them. Also cut its TODO
   pseudo-code to plain words, since the current TODOs are near-solutions and the hints repeat them.
4. **Stop dictating code in TODOs from about quest 08 on.** House style says "TODO says what to write in plain words;
   hints narrow it down; the last hint names the exact call". Many TODOs are the last hint already (01/04, 11, 12, 19,
   22-27). Let the lesson's example be the pattern and the TODO be the goal ("add up every row from 1 to `rows`").
   This is the single biggest win for experienced-dev value, and it makes beginners think instead of type.
5. **Unify the `&` story**: one card in 01/16 that names `&str` vs `String` with a "look vs own" gloss, then reuse that
   exact wording in 17 and 19.
6. **Teach `&&` / `||` / `!`** in 01/10 (one card plus one more test case, e.g. "fragile *and* over 5 kg"), and
   **`println!` + `main`** somewhere in 01-03, since the Run button and two main.rs files already rely on them.
7. **Give experienced devs a "for the curious" line** on a few Rust-distinctive facts: overflow panics in debug and wraps
   in release (07); `as` truncates and saturates, and `From`/`try_into` exist (09); shadowing can change the type (04,
   which is shadowing's real reason to exist, while trimmed text is a weak motivator); `if`/`match` are expressions
   (already done).
8. **Clean the plain flavour**: plain summaries for 17, 19 and 21, plain examples instead of `Chest`/`Mob`/coal, one
   consistent unit chain (crate → sheet → box → pallet) and no theatre or unicorn detours. Move 15 to just before 23,
   and rewrite it without assuming null/exceptions are known ("In many older languages a value can secretly be
   missing; that's called null…").
9. Fix the term ledger: "parameter" is not introduced in 01/03, and `usize`, `pub` and `//` have no rows.

### Rewritten example: 01/05 "Try the obvious thing" (current text is incorrect)

> **Try the obvious thing.** `stock_change` takes two `i32` numbers and returns `after - before`, but its return type
> says `u32`. Rust checks that the types line up before the program ever runs, and they don't. An `i32` minus an
> `i32` is an `i32`, and you promised a `u32`:
>
> ```text
> error[E0308]: mismatched types
>   |     after - before
>   |     ^^^^^^^^^^^^^^ expected `u32`, found `i32`
> ```
>
> **Types, not values.** Rust did not work out that 4 - 10 is negative; it never looks at the numbers. It only
> compared the type you promised with the type you produced. That is why picking the right type matters: the
> type is your promise about every value the function could ever give back. A change can be negative, so its
> promise is `i32`.

### Rewritten example: 01/12 "Parameters stay put" (uses an undefined word)

> **Inputs can't change either.** The numbers a function receives, its **parameters** (the `pile` and `scoop` in
> the first line), are plain `let`s underneath, so they can't change. To count down, make a changeable copy with the
> same name: `let mut pile = pile;`. That is shadowing from quest 4, now with `mut`.

## What a true non-programmer still needs (input for a "programming for beginners" world)

None of these are taught anywhere in 00 or 01:

- **What a program is**, and what "running" one means. There's no `main`, no `println!`, no "the computer does these
  lines top to bottom". Order of execution is never stated, though loops and `return` depend on it.
- **Compiling vs running** ("build" and "compile" are used freely; "compile time" and "runtime" appear only in the 01/15 quiz).
  What the compiler is (01/15 calls it "your first tester", which is good) and why a program can build and still be wrong.
- **What a terminal, console or output is.** The boss lesson says "no terminal is needed", and "Press Run" shows printed output.
- **Values and types as a concept**: text vs numbers vs true/false. The word "string" is never glossed as "text".
  01/05 is the first time "type" is defined, but `u32` is used from 00/03.
- **What a function is**, before 00/01 asks you to fill one. Also inputs/outputs, "calling", and the difference
  between defining and calling.
- **Reading code**: braces as blocks, indentation as readability, `;` as "end of a step", comments, what an error
  message's `-->` file:line and `^^^` mean.
- **What a test is**, and why programmers write them. The whole app runs on them, but a test is only described by
  colour.
- **Basic logic**: and/or/not, and comparisons combined.
- **Lists and repetition in plain terms**, before `Vec`, `for` and recursion arrive in the same boss.
- **Debugging as a habit**: read the first error, change one thing, re-run. 00/02 and 01/02 hint at it, and it
  deserves its own quest.
- **Why other languages have null and exceptions** (or drop the comparison): 01/15 assumes them.
