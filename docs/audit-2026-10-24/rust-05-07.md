# Curriculum audit: Rust worlds 05-traits, 06-smart-pointers, 07-concurrency

Auditor scope: every `quest.toml` and plain `lesson.md` in the three worlds (34 quests), games flavours skimmed
(05/01, 05/03, 05/06, 06/01, 06/04, 06/07, 07/01), starter-vs-solution diffs for 05/04, 05/07, 05/08, 05/10, 05/11,
06/02, 06/07, 06/09, 06/10, 06/11, 07/01, 07/03, 07/08, 07/11. Earlier worlds skimmed by title/tag and by grepping their
lessons for terms these worlds rely on. Read first: `docs/CONTENT.md`, `docs/TRACKS.md`,
`docs/PLAYTEST-2026-10-20-rust-03-06.md`, `docs/PLAYTEST-2026-10-20b-rust-04-06.md`,
`docs/PLAYTEST-2026-10-20b-rust-07-09.md`, `docs/REWRITE-rust-00-01.md`.

**What the earlier playtests already covered (not repeated here):** API calls that appeared only in TODOs/hints
(`rem_euclid`, `is_err`, `split_off`, `mem::take`, `Rc::ptr_eq`, `let-else`, etc.) were patched with "tools" bullets;
quiz answer lengths were rebalanced. Those passes asked "can an LLM who knows Rust solve it from the text?". This audit
asks a different question: does a **true beginner** get the *concept and the why*, and does an **experienced dev** get
Rust's distinctive ideas without padding.

## The headline finding

Worlds 00-01 were rewritten into the golden shape (intro, kicker cards, one idea per quest, situation then name,
the compiler as a character). **Worlds 05-07 never were.** Their plain lessons are cheat sheets: one dense code block,
three to six bullets that *name* things, then "Your turn". The bullets were made longer by the playtest patches
("Tools:", "More small tools:", "Small tools you will need (all new here)"), which fixed "used before taught" for API
calls by turning lessons into the glossary that `CONTENT.md` explicitly forbids. The concepts underneath (heap,
pointer, scope/drop, compile time vs runtime, thread, `'static`) were never taught at all.

Sizing confirms the "one idea per quest" rule is broken: `CONTENT.md` says exercises are 2-8 min and 1-3 objectives.
Twelve exercises run 9-12 min (05/06, 05/07, 05/08, 05/09, 05/10, 06/05, 06/06, 06/07, 07/03, 07/06, 07/08, 07/10)
and six have 4 objectives (05/06, 05/07, 05/08, 05/10, 05/11, 07/07). Each of those is two to four quests in one.

## World 05: Traits & Generics

| Beginner clarity | Experienced-dev value | Coherence/sequencing | Task-lesson fit | **Overall** |
|---|---|---|---|---|
| 4 | 6 | 6 | 7 | **5** |

**Verdict.** The order (trait → default methods → generics → generic structs → dispatch → trait objects → std traits →
operators → Iterator → associated items → impl Trait → boss) is the textbook order and mostly sound, and the tasks are
achievable from the code shown (often too achievable: TODOs and hints transcribe the solution). But the lessons
never say *why* traits exist (shared behaviour without inheritance; Rust has no classes), and they introduce
heavyweight terms (monomorphise, inline, fat pointer, vtable, heap, associated type) as bold words with no picture.
An experienced dev gets a decent tour but misses the ideas that make Rust's trait system distinctive (coherence/orphan
rule, blanket impls, dyn compatibility, `Eq`/`Hash`, `IntoIterator`), and 07-std-traits mostly re-teaches derive,
`Display` and `From` from worlds 02 and 04.

### Worst quests

- **`05-traits/05-static-vs-dynamic-dispatch` (read).** The densest lesson in the world for a beginner: "monomorphises",
  "calls are direct, can be inlined", "fat pointer", "vtable", "its size is unknown", "compile time" vs "runtime", all
  in 4 short paragraphs, none with a concrete picture. "Pointer" itself has never been defined in the track (grep: no
  lesson in 00-04 explains it). "Size is unknown" relies on a stack/heap model never taught. Also placed *before*
  06-trait-objects, so the learner reads the theory of `dyn` before ever writing one. Swap 05 and 06, and give each term
  a gloss tied to the code (see rewrite below).
- **`05-traits/07-std-traits`.** Six ideas in one quest (four derives, `Display`, `From`/`.into()`), 4 objectives,
  10 min. `derive`, `Debug`/`Clone`/`Copy` were taught in `02-ownership/07-clone-and-copy`, `Display` with `write!` in
  `04-errors/01`, `From` in `04-errors/02`. A beginner meets `fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result`
  with no word on what a `Formatter` is or why it is `&mut`. Low value for an experienced dev, overload for a beginner.
  The derive line is literally in the TODO, so objective 1-2 are transcription. Cut to `Default` + `PartialEq` vs `Eq` +
  `Hash` (why you can't derive `Eq` for `f64`, why a `HashMap` key needs `Hash + Eq`); this is genuinely new and
  Rust-specific.
- **`05-traits/08-operator-overloading`.** Teaches an anti-pattern on purpose: `PartialOrd` by length while derived
  `PartialEq` compares fields, with a "Careful:" bullet admitting the inconsistency. An experienced dev learns a habit
  to unlearn; a beginner learns that `<=` and `==` can disagree and doesn't learn why `PartialOrd` is "partial"
  (NaN) or what `Option<Ordering>` means. Also first place `self` is taken **by value** (`fn add(self, ...)`) and `Copy`
  is derived to make it cheap; neither is explained. `type Output` appears here two quests before associated types are
  taught (10). Fix: drop the `PartialOrd` objective (or order by a key that is consistent), explain `self` by value in
  one card.
- **`05-traits/10-associated-types-and-consts`.** The *why* ("why not `trait Convert<Output>`?") is missing, and it is
  the whole point: one impl per type vs many. The starter hands over `where C::Output: Display`, a bound on an
  associated type the lesson never shows. Experienced devs would value the generic-param-vs-associated-type contrast
  (`Add<Rhs>` has both: `Rhs` is a generic, `Output` is associated, which the learner just saw in 08).
- **`05-traits/11-impl-trait`.** Half repeats `03-collections/06-closures`, which already taught `impl Fn(i32) -> i32`
  as parameter *and* return type with `move`. So `impl Trait` syntax was used for two worlds before being named.
  The "one concrete type" rule is stated but not shown failing (the obvious mistake: `if x { a.iter() } else { b.iter().rev() }`)
  — a perfect "let the compiler be a character" moment, unused.

### Best quests (models)

- **`05-traits/02-default-methods`**: one idea, small, the code block shows required vs default vs override side by side,
  hints are progressive. Only missing an intro "why" sentence (the games flavour has one: "Peaceful unless told otherwise").
- **`05-traits/09-iterator-trait`**: strong "write one method, get dozens free" payoff, which is the distinctive Rust idea.
  Best "why" in the world. Would be better still with one line on why `next` takes `&mut self` (the iterator remembers
  where it is).
- **`05-traits/12-boss-shape-renderer`**: good design statement ("dynamic dispatch for the canvas, static dispatch for the
  helpers: that is the point"). Weakness: hints give every formula, so it is near-transcription.

## World 06: Smart pointers

| Beginner clarity | Experienced-dev value | Coherence/sequencing | Task-lesson fit | **Overall** |
|---|---|---|---|---|
| 3 | 6 | 5 | 6 | **5** |

**Verdict.** This is the world where the track's missing memory model hurts most: every lesson leans on "heap",
"pointer", "owns", "freed", "goes out of scope", "dropped", "size known at compile time", and none of those was ever
taught (the word "heap" first appears as a bare assertion in `02-ownership/04` and `03-collections/01`; "scope" and
"dropped" first appear here). A beginner can pattern-match `Rc::clone`/`borrow_mut` into passing tests but will not
understand what problem `Box`, `Rc` or `RefCell` solve. Sequencing has visible seams: `Drop` is promised in quest 02's
folder name but taught in quest 10 (after `Arc` and threads), and `09-arc-preview` introduces threads with no
explanation one world early. Experienced devs get the right toolkit, but nothing on when *not* to use
`Rc<RefCell<T>>` (indices/arenas; the boss itself is ID-keyed), and `Cell` is only in a quiz.

### Worst quests

- **`06-smart-pointers/01-box`.** "Rust must know a type's size" — why? The beginner has never heard of the stack, of
  sizes, or of a pointer. "A `Box` is a pointer to a value on the heap" defines one unknown with two others. Also
  `Cons`/`Nil` are Lisp jargon with no gloss, `use List::{Cons, Nil};` (importing enum variants) is new syntax, and
  "auto-derefs" is used before `Deref` (quest 02). The quest also introduces **recursion** for the first time in the
  track as a single trailing paragraph — that is a quest of its own. Rewrite below.
- **`06-smart-pointers/02-deref-and-drop`.** Title "Deref", folder "deref-and-drop", no Drop. The task is one line
  (`&self.0`). No why: the learner is never told why they'd write their own smart pointer, nor that deref coercion is
  why `&String` works where `&str` is expected (which they've relied on since world 02 — a great "aha" left unsaid).
- **`06-smart-pointers/07-weak`.** The plain lesson contains a sentence leaked from the games flavour: "The pole and
  machine lists live in `RefCell`s so they can change through `&`." There are no poles in the plain story. That bullet
  (assigning through `*cell.borrow_mut() = ...`) also sits *before* the `Weak` bullets it's supposed to support. "Leak"
  is used without saying what a memory leak is or why it matters. `Weak` vs strong count is named but not pictured.
- **`06-smart-pointers/09-arc-preview` + `10-drop-and-cleanup` ordering.** 09 introduces `thread::spawn`, `move ||`,
  `join().unwrap()` and slicing an `Arc<Vec>` in a 5-minute "preview", with no explanation of what a thread is; world
  07 quests 01-02 then teach exactly this again. 10 then needs `requires = ["06-smart-pointers/09-arc-preview"]` and
  teaches `Drop`, which belongs right after `Box`/`Deref` (it's the "freed when it goes out of scope" promise made in
  quest 01). 10's starter also uses `&'static str` and `Guard<'_>`; `'static` is taught nowhere in the track.
  Fix: delete 09 (07/04 already explains why `Rc` can't cross threads), move Drop to 03.
- **`06-smart-pointers/11-boss-tree-editor`.** Still the cliff the 03-06 playtest flagged: the lesson now carries
  "Three things the boss needs" plus a "More small tools" paragraph of eight unrelated APIs. Also a **rendering bug**:
  the source contains a literal newline inside `` `out.push('\n')` `` (lines 32-33), so the card shows `out.push('` and
  `')` split across lines; same in the games flavour. `type NodeRef = ...` (type alias) is in the starter, never taught.
- **`06-smart-pointers/04-interior-mutability` (read).** Doesn't say *why* Rust forbids mutation through `&` in the
  first place, so "the rule is checked at runtime instead" has nothing to hang on. Should open with the concrete
  case: two parts of a program both hold the same chest; one wants to add an item.

### Best quests (models)

- **`06-smart-pointers/03-rc`**: concrete count numbers in comments (1 → 2 → 3 → 2), the inner-block demo makes
  "dropped at the brace" visible, and it says *why* to write `Rc::clone(&a)` instead of `a.clone()`. Good for both
  audiences.
- **`06-smart-pointers/08-cow`**: tight, one idea, real-world why (allocate only when you change), tests check
  `Borrowed` vs `Owned`, which is exactly the lesson. Experienced devs like this one.
- **`06-smart-pointers/06-rc-refcell-graph`**: clear "Rc is shared but read-only, RefCell is mutable but single-owner,
  stack them" framing; the "keep borrows short" warning is the right one.

## World 07: Concurrency

| Beginner clarity | Experienced-dev value | Coherence/sequencing | Task-lesson fit | **Overall** |
|---|---|---|---|---|
| 5 | 7 | 8 | 7 | **6.5** |

**Verdict.** The best of the three worlds. Every lesson opens with a "Why now" tied to the mod-folder hasher, the
sequence (spawn → move → channels → Send/Sync → Mutex → Arc<Mutex> → RwLock → scoped → rayon → atomics → boss) is
well built and each quest's bullets explain consequences ("start every thread before you join any, or you run them one
by one"; "a forgotten `tx` means waiting forever"). Experienced devs get real value: poisoning, scoped threads,
memory `Ordering`, `Send`/`Sync` table. But the world never says what a **thread** is, what a **data race** is, or
why concurrent output is non-deterministic; a beginner will copy the shapes without the mental model. The boss lesson
is again a glossary ("all new here") and has the same literal-newline rendering bug.

### Worst quests

- **`07-concurrency/01-spawn-and-join`.** "Runs work on a second thread" — no definition of thread, no picture of two
  things happening at once, no mention of CPU cores, no demo that the order of `println!`s varies run to run. "Blocks",
  "detached", "panicked" (thread-level) arrive in one bullet list. Solution needs `|&n|` (destructuring a reference in
  a closure), which is first explained in 07/09. Packs `JoinHandle`, `join`, `move` (preview), `.ok()`, panic
  isolation and ordering into a 4-minute first quest.
- **`07-concurrency/08-scoped-threads`.** Opens with "`thread::spawn` demands `'static` data" — `'static` has never
  been taught, and 07/02 explained the same constraint without the word. Then a single bullet introduces `split_at`,
  `chunks`, `.map(|chunk| s.spawn(move || ...))` (with a subtle "move copies the reference" point), and
  `.copied().max()`; the next introduces `split_at_mut`, `chunks_mut`, `iter_mut`, `*x =`. 3 objectives, 10 min,
  really three quests.
- **`07-concurrency/05-mutex`.** Good content, too much of it: guards, `mem::take(&mut *guard)`, deadlock, poisoning,
  `unwrap_or_else` with a closure, `into_inner`. `&mut *guard` (reborrow through a deref) is a genuinely hard piece of
  syntax for a beginner, explained in a parenthesis.
- **`07-concurrency/04-send-and-sync` (read).** Uses "data race" without defining it, "atomic counter" before atomics
  (quest 10), and "marker traits" in the summary. Doesn't make the distinction experienced devs most need: Rust
  prevents *data races*, not *race conditions* (deadlocks and logic races are still possible — 05 and 07 then show
  deadlocks, so say so here).
- **`07-concurrency/11-boss-parallel-file-hasher`.** No games flavour (every other 07 quest has one). Hints give the
  FNV constants and the full pool protocol. `#![allow(...)]` attribute syntax in the starter is never explained.

### Best quests (models)

- **`07-concurrency/02-move-closures`**: the best lesson in all three worlds. Shows the obvious mistake commented out
  with the real compiler message ("closure may outlive the current function"), explains *why* in one sentence
  ("`thread::spawn` cannot know when your function returns"), then the fix, then the consequence (can't use it after).
  This is the golden "situation → it happens → the name" shape.
- **`07-concurrency/03-channels`**: clear metaphor ("threads talk, they don't touch each other's data"), the "forgotten
  `tx` = waiting forever" warning, and tests use `recv_timeout` so mistakes fail instead of hanging (said in the lesson).
- **`07-concurrency/10-atomics`**: explains `Ordering` in plain words at the right depth (Relaxed vs SeqCst, skip
  Acquire/Release for now) and says when atomics stop being enough (two related fields).

### Rewritten example: `06-smart-pointers/01-box/lesson.md` (plain), golden shape

> A to-do list where each item can hold a smaller to-do list inside it is a list that contains itself. Rust needs to
> know how many bytes every value takes before the program runs, and "a list inside a list inside a list" has no end.
> A `Box` is how you break the loop.
>
> **Try the obvious thing.** Write the list as "a number, then the rest of the list":
> `enum List { Item(i32, List), End }`. The compiler stops you with `error[E0072]: recursive type has infinite size`.
> To know the size of a `List` it needs the size of a `List`, forever.
>
> **Two places for values.** Every function gets a small, fixed-size area for its local values: the **stack**, which
> means space that is set up when the function starts and thrown away when it returns. Anything whose size can grow,
> like the text of a `String`, lives somewhere else: the **heap**, a big shared area where a value stays until its
> owner is done with it.
>
> **A pointer is an address.** A **pointer** is a number that says where in memory a value lives. Its size never
> changes, whatever it points to: 8 bytes on your machine. That is what fixes the infinite size.
>
> **Box: an owning pointer.** `Box::new(value)` moves the value to the heap and gives you a `Box`, a pointer that
> **owns** it. When the `Box` goes away at the end of its block, the value on the heap is freed with it. So
> `Item(i32, Box<List>)` is "4 bytes for the number, 8 for the address": a size the compiler can count.
>
> ```rust
> enum List {
>     Item(i32, Box<List>),
>     End,
> }
>
> let list = List::Item(1, Box::new(List::Item(2, Box::new(List::End))));
> ```

(Recursion over the list then becomes its own next quest: "A function that walks the chain".)

### Rewritten example: `05-traits/05-static-vs-dynamic-dispatch`, the dispatch card

> **Two ways to find the method.** With a generic `fn area_of<T: Shape>(s: &T)`, the compiler writes a separate copy of
> `area_of` for each shape you call it with, one for `Circle`, one for `Rect`. This is called **monomorphisation**, which
> means "making one version per type". Each copy knows exactly which `area` to call, so there is no searching while the
> program runs. With `&dyn Shape`, there is only one `area_of`. The reference carries two addresses: one to the shape's
> data and one to a small table listing that type's methods, the **vtable**. Each call looks `area` up in the table
> first. That lookup is the price of putting a `Circle` and a `Rect` in the same `Vec`.

## What a true non-programmer needs that is missing (input for a "general programming for beginners" world)

These three worlds assume a mental model nobody in the track builds:

1. **Memory model**: what memory is, variables as named boxes, stack vs heap, addresses/pointers, why sizes matter,
   what "freeing" memory means and what a leak costs. (Every 06 lesson depends on it.)
2. **Lifetime of a value**: blocks and scope, when a value is created and destroyed, why order of destruction matters
   (files closed, locks released).
3. **Compile time vs run time**: what the compiler checks before the program runs vs what can only go wrong while it
   runs (panics, `RefCell` borrow errors, deadlocks). 05/05, 06/04 and 07/04 all hinge on this distinction.
4. **Abstraction and interfaces**: why you'd want "anything that can be described" instead of a specific type; the
   idea of a contract between code that provides and code that uses. (Traits, generics and `dyn` all assume it.)
5. **Recursion and trees**: a function that calls itself; base case; trees/graphs as data (parent, child, cycle).
   Introduced in a trailing paragraph of 06/01 but used by 06/06, 06/07, 06/11, 07/11.
6. **What a program, process, thread and CPU core are**: one cook vs several cooks in one kitchen; why two cooks
   reaching for the same pot is a problem (data race); why waiting on each other forever happens (deadlock); why the
   order of output changes between runs.
7. **Reading type signatures**: how to read `fn f<T: Display>(x: &T) -> Option<&T>` aloud. By world 05 signatures are
   the main carrier of meaning and no lesson teaches how to parse a nested one like `Arc<Mutex<Receiver<PathBuf>>>`
   (read inside-out: "a shared, lockable receiver of paths").
8. **Libraries and crates as "someone else's code"**: what a dependency is and why the first build downloads (07/09
   has one bullet).
