# Curriculum audit: `gpui` track, worlds 00–05

Scope: `content/tracks/gpui/worlds/{00-setup,01-readings,02-views,03-live,04-sensors,05-taskbar}`. That is 69 quests.
I read every `quest.toml` and `lesson.md`. I compared starter and solution for 00/04, 00/05, 01/05, 01/13, 02/04, 02/05, 02/06, 02/08, 02/12, 03/05, 04/12, 04/14, 05/06 and 05/11.
Reference docs: `docs/CONTENT.md`, `docs/TRACKS.md`, `docs/tracks/gpui.md`, `docs/tracks/gpui-terms.md` and `docs/tracks/rust-terms.md`.
None of these worlds has a flavour, so I had no flavours to skim.

## Headline

The track is well built as a *project*. It is coherent and honest about Windows, and it keeps the house voice. Every quest ships a visible feature of Kinetik, and the plain-Rust "why" paragraphs are often excellent: `None` not `0`, `VecDeque` not `Vec`, `>=` at the limit, why `notify` exists, why tasks must be kept.

The weakness is **GPUI itself**. The mental model is never assembled for a beginner:
- What an *element* is.
- Why styling is a chain of calls.
- Why there are four or five different `cx` types.
- What a *view* really is (an entity whose type implements `Render`).
- Why closures appear in odd places (`debug_selector(|| ..)`, `move`, `.when(.., |el| ..)`).

These are used early and explained late, partly, or never. On top of that, nearly every lesson's single code block **is the answer line**, and "Your turn" says "add the line above". A beginner can turn every objective green by transcribing, without forming the model. An experienced dev gets real value from the Windows and sensor material, but little GPUI depth.

## World 00 Setup — overall 6

**Verdict.** The world is short, friendly, and sets up the cost of the first build honestly. The two exercise quests ask the learner to change two numbers (04) and paste one line (05), and the lesson already prints that line. The GPUI concepts touched are named in a sentence each, without the "why" or the shape of the API: `Application`, `cx`, `open_window`, `Render`, `div`, `.child`, `debug_selector`. `main.rs` (starter) already calls `cx.new(|_| StatsBar)`, `Bounds::centered`, `WindowOptions { .., ..Default::default() }`, `.unwrap()` and `.detach()`, but the lesson glosses only some of them. Two claims build a wrong mental model that a later world has to undo (see below).

**Worst quests**
- `00-setup/05-a-view`
  - The code block is the entire solution: `div().child(div().debug_selector(|| "pill-cpu".into()).child("CPU 12%"))`. "Your turn" says "replace `div()` with the line above".
  - It never explains the `render` signature (`&mut self, _window: &mut Window, _cx: &mut Context<Self>) -> impl IntoElement`), why `debug_selector` takes a *closure*, what `.into()` converts to (`SharedString`), or that `.child` returns the box so calls chain.
  - "View" is defined as "a struct GPUI asks what it looks like". It is not connected to `cx.new(..)` in `main.rs`, which is what makes it a view (an entity); entities wait until `03-live/02`.
- `00-setup/01-what-gpui-is`. "GPUI compares and redraws" is inaccurate. GPUI does not diff the way React does: it rebuilds the element tree and repaints a window when that window was notified. A beginner who arrives with a "virtual DOM" idea keeps it.
- `00-setup/06-it-runs`. "whenever something changes, GPUI calls your view's `render`" directly contradicts `03-live/03-update-and-notify`: "GPUI does not watch your fields … draws only when something tells it to". The quiz then grades the wrong idea ("Whenever the view needs drawing" is defensible, but the lesson text around it says "whenever something changes").
- `00-setup/04-hello-window`. "`.detach()` keeps that rule alive for the whole run" is cryptic. The real idea ("`on_window_closed` returns a subscription; dropping it unsubscribes; `detach` lets it live forever") is the same drop-equals-cancel idiom as `Task` in `03-live/05`, and the two are never connected. The trailing dot in `px(360.)` is also unexplained (f32 literal).

**Best quests (models)**
- `00-setup/03-first-build`. It says what, why (`=` pin because GPUI renames things), and the cost. The `points` question checks exactly the one fact. Short and complete.
- `00-setup/02-msvc-toolchain`. Clear "check yours / if it says gnu" branching.

## World 01 Readings — overall 7

**Verdict.** This is plain Rust with no GPUI, and it is the best-explained world for a true beginner. Every lesson opens with a concrete Kinetik situation and gives the *why*. Examples: `None` versus `0°C` (02); one formatter per unit (03); measure exact, show round (04); `VecDeque` because `Vec::remove(0)` shifts everything (09); `f64::MAX` start values (10). Sequencing is clean, from kinds to units, formats, limits, history and order, ending in a boss that composes them. For anyone who finished the Rust track (the stated prerequisite) it is mostly re-teaching `match`, `while`, `format!` and `swap`, so experienced-dev value is low. Tasks again tend to be "type the shown line", but the boss genuinely requires composition.

**Worst quests**
- `01-readings/13-boss-stat-model`.
  - `let … else`, the `type Snapshot = HashMap<..>` alias, `&'static str` in `Pill`, `*kind` (deref of `&StatKind` in `for slot in order`) and `Option::take` all appear first in the boss. Several of them (`let … else`, `*kind`) appear only in hints.
  - The ledger records them as "boss lesson and hints", which does not meet the "explain, then ask" rule in `CONTENT.md`.
  - The code block (`Some(top) => columns.push(Column::Pills(top, Some(pill.clone())))`) gives away the trickiest line of `two_line_columns`.
- `01-readings/11-bar-order`. The task is to type 11 enum values from prose. It is mechanical and teaches nothing new beyond `vec![]`. It could be pre-filled except for the dividers.
- `01-readings/06-format-speed`. The code block is the complete answer, including the `as u64` that the card just taught.

**Best quests (models)**
- `01-readings/02-a-reading`. A textbook "why": storing 0.0 would draw a real-looking `0°C`, and `None` forces every caller to handle it. It closes with "Callers stay honest".
- `01-readings/09-history`. It motivates the data structure by the cost of the obvious one, says it aloud ("vec-deck"), and the cap paragraph connects to a real setting.
- `01-readings/07-warning-limits`. It matches on a tuple of two `Option`s with a clear "two maybes" framing, and explains `>=` versus `>` with a concrete number.

## World 02 Views — overall 6

**Verdict.** This is the world where a beginner to UI programming most needs the model, and it gives each styling call a one-line gloss but not the system behind it.
- It never says that a `div()` is an *element description* consumed each frame.
- It never names the builder pattern (each call takes the element and returns it, which is why it chains and why `.when` exists).
- The Tailwind-style naming is unexplained: what the `2` in `gap_2` is (a spacing scale step, 8 px at default rem); that `px_2()` (padding-x) is unrelated to `px(..)` (pixels); that `text_color`/`text_size` cascade to children.
- `RenderOnce` versus `Render` is explained in terms of `self` versus `&mut self`. The real reason (a view is a long-lived entity with state, a component is a throw-away value built inside a view's render) depends on entities, which come one world later.
- `cx: &mut App` (RenderOnce) versus `cx: &mut Context<Self>` (Render) appears in starters with no word.

Coherence breaks at the boss: it drops the `PillView` component taught in 05 and asks for a plain `pill_element` function again, with no explanation.

**Worst quests**
- `02-views/05-a-pill-component`.
  - The learner must write `div().debug_selector(move || format!("label-{kind:?}"))…` themselves, but the lesson never says why `let kind = self.pill.kind;` is copied out first and why `move` is needed. The selector closure must be `'static`, so it cannot borrow `self`.
  - `{kind:?}` (Debug formatting) is used to build test names without comment.
  - "GPUI calls it once per frame, and the struct is used up" is true but does not tell a beginner *when* to choose a component over a view.
- `02-views/12-boss-static-bar`.
  - The starter defines `fn pill_element(pill: Pill, show_label: bool) -> Div` with `todo!()`, and hint 3 builds columns from `pill_element`, not `PillView`. The world's headline concept (component, `#[derive(IntoElement)]`) is silently abandoned.
  - The code block is the useless fragment `if self.two_lines {`.
  - Hint 2 relies on `.iter().enumerate()` and the meaning of the divider `index` (unique `debug_selector` names), which the lesson never mentions.
- `02-views/07-dividers`. `.into_any_element()` and `AnyElement` ("so both fit in one `.children(..)`") are the first appearance of a key GPUI and Rust idea: an iterator yields one type, so different element types must be erased to one. It is put in the starter and waved at in one sentence. The very next quest (`08-two-lines`) asks the learner to write `.into_any_element()` themselves.
- `02-views/01-a-row`. It introduces `.gap_2()` as "a small fixed space" without the scale, and `.flex()` without saying what flex layout *is* beyond "along a line". Acceptable for quest 1, but nothing later fills the gap.

**Best quests (models)**
- `02-views/10-numbers-that-sit-still`. A real problem (the bar twitching), an obvious half-fix (monospace) shown to be insufficient, then the real fix, and why 48 (10 px per glyph in tests, narrower on screen). The model for "why".
- `02-views/06-labels-or-not`. It motivates `.when` by "breaking the chain is clumsy", explains what the closure receives and returns, and distinguishes "gone" from "hidden". This is the only place the chain/builder idea is close to explained.
- `02-views/09-the-pill-background`. Alpha is explained as a fourth channel, and it says why the slider changes alpha, not colour.

## World 03 Live — overall 7.5

**Verdict.** This is the strongest GPUI world. It explains entities through the borrow problem ("Rust allows one `&mut` at a time … GPUI holds it for everyone"), maps them onto `Rc<RefCell<..>>` and `Weak` from the prerequisite, gives the classic stale-screen bug its own quest (notify), and makes drop-equals-cancel for `Task` concrete. Timers explain why not `thread::sleep`, and the test clock is explained. An experienced dev learns real GPUI idioms (`_poll` field, `WeakEntity` break, compare-before-notify).

Gaps:
- `cx.spawn(async move |this, cx| ..)` is an **async closure**. The Rust track's Async world only teaches `async move { }` blocks (`grep` over `rust/worlds/08-async/*/lesson.md`), so this syntax is new and unexplained.
- The `cx` inside the spawn is a different context type (`AsyncApp`), and `this` is a `WeakEntity` without being named so until quest 07.
- The family of contexts (`App`, `Context<T>`, `Window`, `AsyncApp`, `TestAppContext`) is never laid out in one place.

**Worst quests**
- `03-live/05-spawn-and-keep`.
  - It introduces async closure syntax, a new context type, `this` (a weak handle, unnamed), `.ok()` discarding a `Result`, and the `Task` drop rule in a single 6-minute quest.
  - The task is changing `let _ = task;` to `self._poll = Some(task);`.
  - The motivation is also weak: after the fix the bar still reads "once and stays there", exactly as calling `tick` directly would. Say plainly that 06 and 07 complete the picture.
- `03-live/13-boss-live-bar`. Hint 4 needs `fn with_interval(mut self, ms) -> Self`, a by-value builder method, without the lesson showing it. The code block is the fragment `if items != self.items {`.
- `03-live/01-state-in-a-view`. Fine on its own, but it is the natural place to say "a view is a struct whose fields are its state; `render` only reads them", and to tie it back to 00/05. It only half does this.

**Best quests (models)**
- `03-live/03-update-and-notify`. The situation (state new, screen stale), the word, the starter's failing test as the "make the mistake" moment, then "Notify, don't draw" (batching). A model GPUI lesson.
- `03-live/02-entity`. It gives the why before the what, connects to the prerequisite (`Rc<RefCell>`), and explains why handles do not block each other.
- `03-live/07-every-second`. `WeakEntity` is explained by analogy to `Weak`, and "Belt and braces" explains why the break is still needed when the task is owned.
- `03-live/09-redraw-only-on-change`. Compare text, not numbers, with a concrete 2.1 versus 2.4 example.

## World 04 Sensors — overall 7

**Verdict.** Excellent domain teaching: what needs admin, why `--` and not `0`, loopback and filter-driver doubles, ACPI dummy values, NVML as an optional DLL, TCP-connect ping. It is valuable to experienced devs, who will not know most of it. For a GPUI learner it is almost entirely non-GPUI until 11–12, and the one big GPUI pattern of the world is pre-written:
- `cx.spawn` on the foreground, then `cx.background_executor().spawn(..).await` for work off the UI thread, then `this.update` back on the UI thread, with `this.read_with(..)` on a weak handle inside `let Ok(..) = .. else { break }`.

The learner adds `: Send`. Several lessons say "this PC" about the *author's* PC, which clashes with the live tests where "this PC" means the learner's.

**Worst quests**
- `04-sensors/12-off-the-ui-thread`.
  - "Already rewired" hides the most important GPUI threading lesson in the track. The lesson never says why `cx.spawn` (foreground) needs no `Send` while `background_executor().spawn` does, how the result gets back to the UI thread (`.await` on the returned `Task`, then `this.update`), or why the sensors moved into `Arc<Mutex<..>>`.
  - The task is a single word (`: Send`). The compile-error moment is good, but it is the only thing learned.
  - Split this quest: one quest writes the background spawn and await, the next meets the `Send` error.
- `04-sensors/14-boss-sensor-hub`.
  - Hint 1 requires `unwrap_or_else(|p| p.into_inner())` (lock poisoning). That idea is taught only in `rust/12-broadcast/15`, which is outside this track's prerequisites.
  - The lesson's code block (`Some(why) => self.missing.insert(kind, why),`) is one arm of a nested match the lesson never shows the shape of.
- `04-sensors/03-skip-loopback` ("On this PC sysinfo lists six adapters…") and `04-sensors/13-why-its-missing` ("This desktop's WMI says 'not supported'"). These describe the author's machine as "this PC". A learner on a laptop is told their CPU temperature reads as "not on this PC". Rewrite as "On the PC this track was written on…" (the phrasing `05-taskbar/04` already uses).
- `04-sensors/08-battery`. It says "bit 8" and "bit 128" for the bits whose *values* are 8 and 128 (bit 3 and bit 7). That is misleading for anyone who later reads Win32 docs. Say "the 8 flag" or "the bit worth 8". The quiz prompt repeats the error.

**Best quests (models)**
- `04-sensors/01-what-needs-admin`. A read quest that earns its place: it sorts every stat into free, driver or admin, and states the "never pretend" rule the whole world enforces.
- `04-sensors/05-gpu-via-nvml`. It frames "three things can fail", then shows how `.ok()?` turns each into `None`. Clear, idiomatic, honest about the no-NVIDIA case.
- `04-sensors/09-ping`. It explains the deviation from Kinetik (TCP instead of ICMP, and why), and plants "feel the cost" so quest 12 has a felt motivation.

## World 05 Taskbar — overall 6.5

**Verdict.** This is real-world Windows knowledge that is hard to find elsewhere: `Shell_TrayWnd`/`TrayNotifyWnd`, `WS_EX_TOOLWINDOW` via `PopUp`, `focus: false` and why, physical versus logical pixels, the 8-px invisible frame, the `display_id` trap, auto-hide detected by intersecting with the monitor. The `WinApi` trait seam with a recording fake is a valuable design lesson for experienced devs. For beginners:
- HWNDs, window classes, `w!(..)`, `Result<HWND>` from `FindWindowW`, `raw-window-handle` and `SetWindowPos` flags arrive as one-line glosses.
- Lessons leak internal planning jargon ("Spike R3 in the plan").

The boss lesson references a function that never existed, and the boss starter's `main.rs` runs a detached loop that never breaks, contradicting `03-live/07`.

**Worst quests**
- `05-taskbar/11-boss-docked-bar`.
  - The lesson says "the world's earlier `redock` and `check_fullscreen` are folded into the one `tick`". No quest or starter in world 05 has a `check_fullscreen` (grep finds none); quest 08 wrote `covers_monitor` and `bar_visible`.
  - `starter/src/main.rs` does `cx.spawn(async move |_, cx| { loop { timer.await; docker.tick(); } }).detach();`. That is an unbreakable detached loop, exactly what `03-live/07` warns about ("any loop you ever `detach`").
  - "Stop it from Task Manager" is a poor beginner experience. A `cx.quit()` on Ctrl+C or a debug close is worth adding, or at least name `taskkill`.
- `05-taskbar/02-see-through`, `05-taskbar/05-dpi` and `05-taskbar/09-every-taskbar`. "Spike R3 in the plan put this window over white, black and red backdrops…" and "Spike R3 found…". The learner has never seen "the plan" or a spike; this is author-facing language. Rephrase as "When this track was tested, …".
- `05-taskbar/06-stay-on-top`. It introduces four ideas in one quest: the trait seam, the recording fake, topmost/`SetWindowPos`, and the HWND via `raw-window-handle`. That breaks the "one idea per quest" rule. The task itself is trivial (`self.api.set_topmost(self.hwnd)` twice).
- `05-taskbar/03-find-the-taskbar`. HWND (what a window handle *is*), `w!(..)` (a wide UTF-16 string literal, and why Win32 needs it) and why `FindWindowW` is `unsafe` at all are each half a sentence or less.

**Best quests (models)**
- `05-taskbar/01-window-options`. Each field gets its user-facing reason, `focus: false` especially, and the point checks the reason, not the syntax.
- `05-taskbar/04-dock-maths`. A real measured auto-hide case (y 1438–1486 on a 1440 monitor) motivates `intersect`. It is pure maths with exact tests and good "why".
- `05-taskbar/08-hide-in-fullscreen`. Clear definition of "covers", maximised versus fullscreen, and a sane default for `None`.

### Rewrite example: `00-setup/05-a-view`

Current (cards 2–5): "**The word for it.** What fills a window is a **view** …", "**Boxes in boxes.** The building block is `div()`, an empty box. `.child(...)` puts something in it …", plus a code block that is the full answer.

Proposed:

> The window is empty. Kinetik's bar is a row of small boxes, one per stat, each holding a label and a number. Start with one: a box that says `CPU 12%`.
>
> **The word for it.** What fills a window is a **view**: a struct that GPUI keeps for you and asks, "what do you look like right now?". `main.rs` makes one with `cx.new(|_| StatsBar)` and puts it in the window. World 03 shows why GPUI, not you, holds it.
>
> **Render answers.** A view implements the `Render` trait. Its one method, `render`, gets the view (`&mut self`), the window and a context, and gives back an **element**: a description of what to draw this frame, not the drawing itself. `impl IntoElement` means "some kind of element; the compiler knows which".
>
> **Build by chaining.** `div()` makes an empty box. Each call after it, like `.child(..)`, takes the box, changes it and hands it back, so calls line up: `div().child("CPU 12%")`. This is called a **builder**, and every look on the bar (colours, sizes, rows) is one more call in the chain.
>
> **A name for tests.** `.debug_selector(|| "pill-cpu".into())` names a box so a test can find where it was drawn. It takes a closure because GPUI only asks for the name in debug builds; in release the closure never runs. `.into()` turns the text into GPUI's string type.
